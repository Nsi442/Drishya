# Deploying Drishya

> **There are two deployment paths, and this is the cheap one.** For AWS — RDS,
> EC2 and CloudFront in a single CloudFormation stack — see
> [`AWS-DEPLOYMENT.md`](AWS-DEPLOYMENT.md). It is the target `CLAUDE.md`
> describes, and unlike everything below it **bills by the hour**. Pick one;
> they are alternatives, not layers.

Three providers, each doing the one thing it is good at:

| Layer | Provider | Why |
|---|---|---|
| Database | **Neon** | Postgres with PostGIS built in, free tier that does not expire, scales to zero between demos |
| Backend | **Render** | Deploys a Dockerfile directly, gives HTTPS, no load balancer to pay for |
| Frontend | **Vercel** | Static Vite build, HTTPS by default, previews per branch |

**HTTPS is not polish here.** Browser geolocation refuses to run outside a secure
context, so `source: BROWSER` positions only work on the deployed URL. All three
providers give HTTPS as standard.

---

## Order matters

Neon first, then Render, then Vercel. Each step needs a value from the one
before it.

---

## 1. Neon

1. Create a project on **PostgreSQL 16** — the same major as
   `docker-compose.yml`. Neon offers newer; a query that behaves on 17 locally
   and differently on 16 in production is exactly the fault that surfaces the
   morning of a review.
2. Run [`db/neon-setup.sql`](db/neon-setup.sql) once, in the SQL Editor or via
   `psql`. It enables PostGIS and then proves it works with a real distance
   calculation. **If that returns no rows, stop** — every geofence check and
   lane calculation in this system is a PostGIS query, and the schema will not
   even parse without the geography type.
3. Copy the **direct** connection string, not the pooled one.

> **Direct, not pooled.** Neon's pooler is PgBouncer in transaction mode, which
> breaks the server-side prepared statements Hibernate relies on. A long-lived
> JVM holding a five-connection Hikari pool has no use for an external pooler
> anyway.

Convert what the console shows into what Spring wants:

```
console    postgresql://user:pass@ep-xxx.aws.neon.tech/drishya?sslmode=require
↓
JDBC url   jdbc:postgresql://ep-xxx.aws.neon.tech/drishya?sslmode=require
username   user
password   pass
```

`?sslmode=require` is mandatory — Neon refuses plaintext.

Flyway runs the migrations on first boot. No schema step is needed here.

## 2. Render

Push the repo, then **New → Blueprint** and point it at
[`render.yaml`](render.yaml). Everything except the secrets is declared there.

Set these four in the dashboard (they are `sync: false`, so Render will prompt):

| Variable | Value |
|---|---|
| `SPRING_DATASOURCE_URL` | the JDBC url from step 1 |
| `SPRING_DATASOURCE_USERNAME` | Neon user |
| `SPRING_DATASOURCE_PASSWORD` | Neon password |
| `CORS_ALLOWED_ORIGINS` | your Vercel URL — fill in after step 3 |

`INTERNAL_SERVICE_TOKEN` is generated by Render. You need its value to call the
training export; read it from the dashboard.

**Health check is `/actuator/health/readiness`, not `/health`.** Liveness goes
green as soon as the JVM is up, which is well before Flyway has migrated and the
seeder has run — Render would start routing traffic into 500s.

Verify:

```bash
curl https://drishya-api.onrender.com/actuator/health/readiness
curl -X POST https://drishya-api.onrender.com/api/auth/demo-login \
     -H 'Content-Type: application/json' -d '{"role":"vendor_admin"}'
```

## 3. Vercel

**New Project → import the repo**, then set the root directory to
`Drishya Frontend/drishya_frontend`. [`vercel.json`](Drishya%20Frontend/drishya_frontend/vercel.json)
handles the rest.

One environment variable:

| Variable | Value |
|---|---|
| `VITE_API_BASE` | `https://drishya-api.onrender.com/api` |

Note it is `VITE_API_BASE`, and it **includes the `/api` suffix** — that is what
[`services/client.js`](Drishya%20Frontend/drishya_frontend/src/services/client.js)
expects. Left unset it defaults to a relative `/api`, which works locally
through the Vite proxy and 404s everywhere else.

Vite inlines `VITE_*` at build time, so changing it needs a redeploy, not a
restart.

**Then go back to Render** and set `CORS_ALLOWED_ORIGINS` to the Vercel URL.
This is the first thing that breaks on a real deploy: locally the Vite proxy
keeps the browser on one origin and CORS never comes into it, but Vercel and
Render are genuinely different origins. Include preview URLs if you want branch
previews to work:

```
https://drishya.vercel.app,https://drishya-git-main-you.vercel.app
```

### Why the odd rewrite rule

```json
{ "source": "/((?!assets/).*)", "destination": "/index.html" }
```

React Router does client-side routing, so a hard refresh on `/vendor/shipments`
asks Vercel for a file that does not exist. The rewrite serves `index.html` for
everything **except** `/assets/`, which must keep 404ing properly — a missing
JS chunk that silently returns HTML produces a blank page and a
`Unexpected token '<'` in the console, which tells you nothing about the real
cause.

## 4. Verify it end to end

The point is not that the pages load — it is that a position posted to the
hosted API appears on the hosted map.

```bash
python simulator/simulate.py \
  --shipment SHP-24025 \
  --api-url https://drishya-api.onrender.com \
  --time-scale 120
```

Then open the Vercel URL, sign in as `priya@anandauto.example` / `drishya`, and
watch the vehicle move on the live map.

> **Status: not performed.** The configuration in this repository is written and
> internally consistent, but it has **not** been deployed or tested against real
> Render, Vercel or Neon accounts — those do not exist yet. Everything above is
> verified locally against Docker Postgres + PostGIS only. Treat the first
> deploy as debugging, not as confirmation.

## Free-tier behaviour you need to plan around

**Render free web services spin down after 15 minutes of inactivity** and take
roughly 50 seconds to wake. Two consequences:

- The first request in a demo will appear to hang. **Wake the service a few
  minutes before presenting** by loading the health endpoint.
- The `@Scheduled` ETA cycle stops while the service is down. Predictions resume
  on wake; they do not backfill.

**Neon suspends idle compute**, and the 60-second ETA cycle keeps it awake
whenever a trip is active. That is correct while vehicles are moving and pure
waste overnight. `ETA_CYCLE_MS` on Render is the knob — raise it, or suspend the
service, when nothing is running.

**Neon free storage is limited** (0.5 GB at time of writing). The `positions`
table is the only one that grows meaningfully: roughly 331 rows per simulated
trip. Thousands of demo trips would matter; tens will not.

### Cost guardrails

All three tiers are free and **none bills by the hour**, which removes the
category of risk the original AWS plan needed a teardown script for — there is
no RDS instance to leave running.

Still worth doing:

- Set a spend limit on Render and Neon (both support one) so a plan change
  cannot silently start billing.
- `scripts/teardown.sh` deletes the deployed resources when the review is over.

## The local path still works

Nothing above is required to run Drishya. The offline fallback is unchanged, and
it is what to use if the venue network fails:

```bash
docker compose up -d db
cd Drishya.Backend && ./mvnw spring-boot:run
cd "Drishya Frontend/drishya_frontend" && npm run dev
```

Local uses Docker Postgres on port **5433** (5432 is taken by a local
PostgreSQL service on this machine), no SSL, and the Vite proxy — so CORS never
comes into it.
